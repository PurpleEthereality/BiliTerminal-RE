**两条审计结论的更正（重要，勿按原描述重复修）**

1. **S3 的前提是错的。** 反编译 `okhttp-4.12.0.jar` 的 `okhttp3.ResponseBody` 可见 `string()` 与 `bytes()` 内部都是 `source().use { … }`（字节码调用 `CloseableKt.closeFinally`），即**读完 body 就会把连接归还连接池**。因此「所有 API 的 Response 从不 `close()`，连接与文件描述符被占用」不成立；真正泄漏的只有「body 从未读完就丢弃 `Response`」的 10 处路径（已全部修掉）。原报告点名的 `UserInfoApi.java:323/:368`、`ReplyApi.java:254` 经核实走 `bytes()` 读完，**不是泄漏**。
2. **`IjkPlayerBridge.release()` 不能简单地 cancel `job`。** 原报告的建议（「`release()` 仍只 cancel `progressJob`、不 cancel `job`」）按字面执行会造成功能回归：`release()` 并非终结路径 —— `activity/video/ShortVideoPlayerActivity.kt:243` 的 `onViewRecycled` 会调用它，同一个 holder 随后还会 `initPlayer()` → `createPlayer()` 复用；若顶层 job 已被取消，`startProgressTracking()` 会 launch 到已取消的 scope 里静默失效（进度条从此不动）。正确做法是 `scope.cancel()` 后**立即重建** scope，已按此实现（`player/IjkPlayerBridge.kt:41-44`、`release()` 末尾）。

### M6. 任意 `IOException` 都重试 5 次，最坏 120 秒，且对写操作不安全

**位置**：`app/src/main/java/com/RobinNotBad/BiliClient/util/NetWorkUtil.java:268-314`

```java
int maxRetries = Math.max(1, SharedPreferencesUtil.getInt("api_retry_max_times", 5));   // :269
...
for (int attempt = 1; attempt <= maxRetries; attempt++) {          // :275
    response = client.newCall(request).execute();
    if (!isDoctypeResponse(response)) return response;
} catch (IOException e) {                                          // :292
    lastException = e;
```

**问题**：`executeWithDoctypeRetry` 是几乎所有 GET/POST 的统一入口，`catch (IOException)` 把「风控 DOCTYPE 拦截」与「超时 / DNS 解析失败 / 连接被拒」一视同仁地重试。配合 `NetWorkUtil.java:124-126` 的 `connectTimeout(8s)` + `readTimeout(16s)`（**无 `writeTimeout`、无 `callTimeout`**），一次最坏 `5 × (8+16) = 120` 秒。

**并且 `maxRetries` 无法被用户调低**：它从 SP key `api_retry_max_times` 读取，但实测 `grep -rn "api_retry" app/src/` **只命中 NetWorkUtil 自己那 4 行**，全仓库没有任何设置项写入这两个 key。

**写操作风险**：`executeWithDoctypeRetry` 也会被提交类请求经过，重试可能造成**重复提交**（重复发评论 / 重复点赞），因为这些接口没有幂等保护。

**修复方向**：区分异常类型（只对超时/连接类重试，DNS 失败不重试），加 `callTimeout`，非幂等请求禁止重试，并把重试次数暴露到设置页。

## 四、贯穿性观察

上述条目看似零散，实则同一病根：**这个仓库有一流的文档，零执行机制。**

| 文档约定 | 实际状态 |
|---|---|
| `AGENTS.md`「调试入口必须用编译期常量 `BuildConfig.DEBUG`」 | `SplashActivity.kt:127` 用运行期判断违反它，无人发现 |
| `AGENTS.md`「每步要 assembleDebug + 单测通过」 | CI 不跑测试（M13），约定只约束人 |
| `AGENTS.md` 记录了 `start()` 无同步 | 至今未修（S5），并派生出更隐蔽的 `recoverStuckSections` 放大路径（S6） |
| `proguard-rules.pro` 每条规则都有注释解释理由 | 理由是错的（`Class.forName` 不存在，S10），25 行指向早已移除的依赖 |
| `PrivateMsgApi.java:237` 的注释证明修过日志泄漏 | 漏掉了私信正文那两条（M12） |
| `TerminalContext.leaveDetailPage` 有完整 Javadoc 承诺 | 方法体为空（M3） |

**结论：这个项目最大的不足不是任何单条缺陷，而是质量依赖人的记忆而非机器的强制。** 而那些"改一两行永久解决"的（CI 加一行测试、WBI 两行换序、`split("=", 2)`、删无用权限）恰恰是收益最高的。
